# Device-seat Turnstile setup

This source candidate verifies a Cloudflare Turnstile token when a browser opens a **new** device seat. Verified seats are not challenged again. The verification step is shared by the normal Join button, one-tap wish join, Sidekicks and the direct Host flow. The server validates the token before setting a session cookie and checks the returned action and exact site hostname. While enabled, it also requires a server-signed proof cookie on every authenticated request, so a browser cannot invent a session token to bypass the challenge.

The current client implementation in `app/seat-challenge.ts` explicitly renders the widget with `action: 'seat'`, which matches the server-side `result.action === 'seat'` requirement in `lib/seat-turnstile.ts`.

Turnstile is disabled until the deployment owner configures all four server-side settings:

| Setting | Purpose |
| --- | --- |
| `TURNSTILE_ENABLED=true` | Explicitly enable verification for new seats |
| `TURNSTILE_SITE_KEY` | Public widget key, returned to the browser when verification is needed |
| `TURNSTILE_SECRET_KEY` | Private Siteverify key; never expose it to the browser or Git |
| `MOMO_SEAT_SIGNING_SECRET` | Separate random secret of at least 32 characters for signing device-seat cookies |

Create a widget in the intended Cloudflare account and allow only the exact deployed hostnames that should issue seats. Use a separate widget for a disposable preview. If the enable flag is true but any required setting is missing, new seats return 503 without a cookie. If verification fails, the server returns 403 without a cookie. Seats created before the flag was enabled need to pass the challenge once; their existing device token is then signed, preserving their profile and joins. Rotating `MOMO_SEAT_SIGNING_SECRET` invalidates signed seats and requires a migration plan.

Cloudflare also publishes official Turnstile test keys for automated/test environments. Those are useful for checking UI wiring in a disposable preview, but they are not a substitute for the final real-widget production check and must never be configured in production. The final replay/hostname/action verification should use the real disposable-preview widget because production Siteverify behavior is what the launch gate is intended to prove.

## Disposable hosted verification

`tests/hosted-turnstile-probe.mjs` is the reviewed backend activation probe. It refuses the known production hostname and expects a fresh token generated by the same disposable preview hostname.

PowerShell example from the repository root:

```powershell
$env:MOMO_TURNSTILE_TEST_DISPOSABLE = 'yes-verify-preview-seat'
$env:MOMO_HOSTED_TEST_APP_URL = 'https://YOUR-DISPOSABLE-PREVIEW.example'
$env:MOMO_HOSTED_TURNSTILE_TOKEN = 'FRESH-TOKEN-FROM-THAT-PREVIEW'
node tests/hosted-turnstile-probe.mjs
```

The probe verifies all of the following:

- a fresh seat first receives HTTP 428 and no session cookie
- a valid real Siteverify result creates both `momo_sid` and signed `momo_seat`
- the verified seat can reach member APIs
- replaying the same token from a new session is rejected
- a forged unsigned `momo_sid` cannot reach member APIs while Turnstile is enabled

Do not save the fresh Turnstile token in Git, shell history shared with others, screenshots or issue/PR text. It is short-lived and should be discarded after the probe.

## Before enabling production

1. Deploy the reviewed source to a disposable preview with a separate widget and the four settings above. Do not use production participant records.
2. Run `tests/hosted-turnstile-probe.mjs` and record the pass/fail result, not the token.
3. Confirm the widget works from Ghar, one-tap wish join, Sidekicks and direct Host login on desktop and a physical mobile device. Confirm cancel and network errors leave the visitor signed out.
4. Confirm a pre-existing disposable seat can complete the challenge without losing its profile/joins.
5. Confirm the Turnstile dashboard records the expected server-side Siteverify calls.
6. Configure the current public perimeter rate limit using **Vercel Firewall** as described in `docs/EDGE_RATE_LIMIT_SETUP.md`. The public app currently uses a `vercel.app` hostname, so Cloudflare WAF does not front those requests merely because Momo also uses Cloudflare D1/Workers.
7. Only after those checks, set the real production widget/site key, secret key, seat-signing secret and `TURNSTILE_ENABLED=true` on the intended production deployment.
8. Recheck Ghar, one-tap wish join, Sidekicks and Host after the production deployment. If the challenge fails unexpectedly, unset/disable the production flag rather than weakening hostname/action validation.

The challenge token is single-use and expires after five minutes, according to Cloudflare's server validation guidance. The widget uses explicit rendering and the CSP admits only Cloudflare's challenge script/frame origin. The browser never receives the secret key.
