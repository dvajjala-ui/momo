# Momo to Pizza — gap and risk audit

Audited 2026-11-02 against `main` at `f20a205` (last commit 2026-10-22; 288 tracked files, ~360 KB of app/lib source). Four passes: launch gates and docs, security and data integrity, product funnel and features, engineering health. Every Critical and High item below was re-verified directly in source; the file:line evidence is in each item.

## Verdict

The security perimeter is genuinely good. The product cannot currently complete its own promise.

A member can discover a plan and ask for a seat, but nothing can be confirmed, notified, or attended: email sending is flag-gated off, WhatsApp is draft-only, publishing a plan notifies nobody, and there is no post-event path at all. Live production confirms the funnel has never carried a real meetup — `GET /api/community` returns `{"events":[],"gallery":[],"wishes":[],"pilot":{"active":3,"capacity":100}}`. There is no CI, so nothing below is policed by a machine.

## Verified strengths (do not regress these)

- All SQL uses bound parameters; the only interpolated fragments are server-controlled room shapes plus `?` placeholders (`lib/chat-core.mjs:6`, `app/api/community/route.ts:75`). No injection surface found.
- No endpoint trusts a browser-supplied role, `userId`, or identity header. All mutating POSTs enforce `sameOrigin` and HttpOnly/Lax/Secure cookies. `GET /api/admin` unauthenticated returns 403 on live production.
- The 3-group cap and per-gang seat cap are atomic guard-inserts (`app/api/community/route.ts:108,121`); deterministic primary keys on `wish_joins`, `blocks`, `direct_threads`, `event_attendance` make the missing UNIQUE indexes unexploitable.
- No SSRF or open-proxy path: gateway and chat URL validators reject credentials, query, path and `http` (`lib/d1-http.ts:19`, `lib/realtime.ts:10`, `lib/image-sanitizer.ts:9`). Gateway and chat secrets never reach the browser.
- WhatsApp sending is real fail-closed: `lib/whatsapp.ts:9` requires `WHATSAPP_WEBHOOK_PUBLIC` **and** `WHATSAPP_PHONE_VERIFICATION_READY` (both `false` in `.env.example`), plus verified phone and consent revision. Webhook HMAC is verified with monotonic state (`app/api/whatsapp/webhook/route.ts:5`). Turnstile verification fails closed and binds hostname + action (`lib/seat-turnstile.ts:26`).
- Accessibility is better than typical: skip link, `:focus-visible`, `prefers-reduced-motion`, focus-trapped modals with `inert`, live-region announcements (`app/globals.css:20,455`; `app/momo.tsx:58`).

## Critical — nothing works until these are closed

1. **No CI, no test command.** `.github/` does not exist; `package.json` has no `test`, `typecheck`, `db:migrate`, or format script. Twenty-five test files are run by hand, and `buildCommand` (`vercel.json`) only typechecks as a side effect of build. A broken `main` reaches Vercel unblocked, and per `AGENTS.md:12` GitHub pushes never deploy the Sites artifact at all, so the two targets drift with no gate.
2. **`ADMIN_EMAILS` is documented as the host allowlist and exists nowhere in code** (0 matches across `app/`, `lib/`, `cloudflare/`, `scripts/`, `db/`, `tests/`). `AGENTS.md:11` and `docs/SECURITY_REVIEW.md` both lean on it. Host identity is in fact one shared passcode, so `admin_audit.actor_id` cannot distinguish operators and there is no per-admin revocation.
3. **Email invitations cannot send, and the failure is invisible.** `emailConfig()` counts `EMAIL_SENDING_ENABLED !== 'true'` as a missing key (`lib/email.ts:10`, default `false` at `.env.example:57`), and every outbound path throws first (`lib/email.ts:31,44,67`). Provider code itself is complete (`lib/email-provider.ts:18`). Because the member's "Send my confirmation link" button only renders when `me.emailConfigured` (`app/email-invitations.tsx:56`), the whole verify → review → send step is not just disabled, it is absent from the UI.
4. **Every real image upload fails, and the test suite cannot catch it.** `cloudflare/db-gateway/worker.mjs:53` rejects when `info.format !== request.headers.get('content-type')`; the image pipeline returns a short format (`png`, `jpeg`) while the header is a MIME type (`image/png`), so the comparison is always false → 422 → "Photo processing is unavailable" (`app/api/upload/route.ts:30`). The mock in `tests/image-sanitizer.integration.mjs:11` returns `format: 'image/png'`, which is why the suite passes. Note `docs/SECURITY_REVIEW.md:113` and `CODEX_HANDOFF.md:113` both record production upload checks as having passed — re-verify before trusting that claim.

## High — breakage and exposure

5. **Host passcode is brute-forceable.** The lockout bucket is keyed to the attacker's own device cookie (`app/api/session/route.ts:36`, `limitId = sha256('host-login:' + current)`) and seats are free to mint (`app/api/session/route.ts:26`); production Turnstile is off by owner decision. Clearing cookies resets the 6-per-10-minutes budget against the only host credential. Fix: bucket by IP/edge rule, server-side.
6. **The 100-seat pilot is trivially exhaustible.** `lib/member-access.ts:7` grants `active` while `COUNT(status='active') < 100`, and any visitor can claim a seat through `profile` (`app/api/community/route.ts:97`) with no CAPTCHA and no per-IP limit. One script permanently moves every legitimate member to `queued`. Fix: edge rate-limit `/api/session` and `profile`, or protect seat creation.
7. **Server failures return 400 and are never logged.** `app/api/community/route.ts:149`, `app/api/admin/route.ts:158`, `app/api/direct/route.ts:69`, `app/api/session/route.ts:49` catch everything, emit nothing, and answer 400. A D1 or gateway outage presents as a client error and is invisible to monitoring; the redacted sink covers only five named events (`lib/ops-log.mjs:1`). Fix: distinguish validation errors (400) from dependency failures (503) and log the latter.
8. **Account deletion can fail permanently.** `lib/r2-bucket.ts` `delete()` throws on any non-ok response including 404 (unlike `get()`, which tolerates 404), and `lib/member-lifecycle.ts:6` awaits that delete *before* the transaction. A member whose photo object is already gone can never delete their account; when `BUCKET` is unset the delete is skipped and participant photos are orphaned in R2. Fix: tolerate 404, move cleanup after the committed batch.
9. **Capacity is validated then discarded.** `lib/host-plan.ts:18` enforces 2–100 but only bakes the number into description text (`:24`). `events` has no capacity column (`db/schema.ts:4`) and `app/api/admin/route.ts:141` inserts `event_attendance` with no cap check → unbounded over-booking of a real venue.
10. **Publishing a plan notifies nobody, and two membership systems never reconcile.** Wish joins are device-seat based (`app/wishes.tsx:34`, `app/api/community/route.ts:121`) while a plan "place" is an `email_invites` row (`lib/email.ts:34`). Publishing a plan for a wish (`app/api/community/route.ts:137`) inserts an event and sends no letter, no host note, no push; members must rediscover it on the wall. Host notes are per-single-member only (`app/admin-console.tsx:66`).
11. **The Attend step is silently blocked for one-tap joiners.** Home advertises step 02 as needing no profile (`app/home-playful.tsx:36`), but the attendance roster and the attendance write both read `FROM profiles` (`app/api/admin/route.ts:44,139`). A member without a chat profile can never be marked attended, therefore never earns the "met at Momo" trust mark (`app/trust-marks.tsx`), and `canUseDirectThread` stays false (`lib/member-access.ts:19`) — a dead end with no message.
12. **Nothing exists after the event.** No RSVP or decline, no reminders beyond a manual `.ics` that omits `DTEND` even though the host captured a planned finish (`lib/host-plan.ts:24` vs `lib/plan-calendar.ts:21`), no no-show state (only "not recorded", `app/admin-console.tsx:60`), no feedback or recap, no cancellation flow. Past plans vanish from every member surface (`lib/plan-discovery.ts:10`), and gallery photos are fetched (`app/api/community/route.ts:60`) but never rendered anywhere in `app/*.tsx`.
13. **No rate limiting on uploads or reports.** `app/api/upload/route.ts:15` allows unlimited 3 MB posts (chat has a 3-second throttle; uploads have none), and `app/api/community/route.ts:106` inserts a fresh `reports` row per call with `crypto.randomUUID()` — no dedup, no per-user cap.
14. **The caps that define the pilot are not schema-enforced.** `db/schema.ts` has no CHECK constraint, nothing caps `member_controls.status = 'active'`, and `events.capacity` / `wishes.spots` are plain integers guarded only by UI `max={100}` and app code. No down-migration or rollback SQL exists anywhere in `drizzle/`.
15. **`pnpm db:generate` can corrupt the schema.** `drizzle/` has 11 migrations and 11 journal entries but snapshots only for `0000`–`0008` (`0009`/`0010` are hand-authored, including the `nickname_claims` backfill). A generate diffs against the `0008` snapshot and can emit duplicate or contradictory DDL, and `vercel.json`'s `buildCommand` runs `embed-migrations.mjs`, whose generated bundle is fed to Vercel's auto-apply (`lib/sqlite-d1.ts:52`) with no test ever validating it.

## Medium

- **Local credential file in the project root.** `.env.cloudflare.local` (gitignored at `.gitignore:32`, never committed) holds live `CLOUDFLARE_D1_API_TOKEN` and R2 access/secret keys. `CODEX_HANDOFF.md:52` says these temporary copies "were removed after verification" — they were not. Rotate the token and delete the file. Related: `lib/sqlite-d1.ts:77` falls back to `/tmp/momo.sqlite` when gateway/D1 are unset, so a config failure silently writes to an ephemeral file while routes report success.
- **Email tombstone blocks re-invitation.** `lib/member-lifecycle.ts:9` preserves `email_deliveries.id` = `tokenHash(email + ':' + eventId)` while `lib/email.ts:71` does `INSERT OR IGNORE` and throws when `changes === 0`. Once an address received a letter for an event, it can never be invited to it again, even from a fresh account.
- **Unbounded full-table write on deletion.** `lib/member-lifecycle.ts:22`'s `UPDATE wishes SET status=…` has no `WHERE`; it rewrites every wish and races concurrent joins.
- **Media access ignores seat status.** `app/api/media/[id]/route.ts:2` grants any valid session (and `gallery` rows, unauthenticated) read of member photos with no `memberIsActive` check, so suspended or queued seats keep pulling photos.
- **Host header reflected into calendar output.** `app/api/plans/[id]/calendar/route.ts:13` writes the request `Host` into ICS `UID@host`/`URL` via `lib/plan-discovery.ts:16`.
- **Non-constant-time secret comparisons.** `lib/device-session.ts:34` compares `proof === await hostProof(...)` while `equalProof` exists one line above; `app/api/whatsapp/webhook/route.ts:4` compares `hub.verify_token` with `!==`.
- **Unbounded table growth.** `chat_send_receipts`, `email_deliveries`, `host_login_limits`, `admin_audit` are never pruned; only `email_budgets` is (`lib/email.ts:46`).
- **Naming drift and duplicate CTAs.** wish / gang / plan / seat / letter / postcard / adda / sidekick coexist on one screen with four join verbs — "Ask for a seat" (`app/upcoming-plans.tsx`), "Join in one tap" (`app/wishes.tsx:34`), "Save my request" (`app/email-invitations.tsx:42`), "Save my spot" (`app/momo.tsx:112`). Email and WhatsApp invite lists are both shipped in parallel.
- **Silent misrouting and hidden gates.** `/chat?room=w_x` falls back to `weekend` when the seat is not in the gang (`app/momo.tsx:37`) with no explanation. The 100-seat banner (`app/momo.tsx:86`) needs a `member_controls` row that only exists after a first rejected attempt, so the capacity gate is discovered only on submit. `?view=sidekick` (`app/api/community/route.ts:63`) is never called, so applicants get no status view.
- **Half-wired UI.** `app/letters.tsx` (Letters + BadgeMaker) is imported nowhere; `Cast`/`SLOGANS` in `app/brand.tsx:19` are unused; profile photos render and the upload API accepts `kind=profile`, but no member upload UI exists. `AdminConsole` shows "No matching seats" *while loading* and keeps one never-cleared error string (`app/admin-console.tsx:29,53`), while `app/email-inbox.tsx:58` does loading/retry properly. Notices fail silently via `.catch(() => {})` (`app/momo.tsx:57`), and one shared toast slot per page (`app/momo.tsx:125`) clobbers messages.
- **Hardcoded identifiers.** `metadataBase` is pinned to the Vercel preview domain (`app/layout.tsx:7`) while email links use `EMAIL_PUBLIC_URL`; `database_id` is duplicated in `cloudflare/chat/wrangler.jsonc:7` and `cloudflare/db-gateway/wrangler.jsonc:12`; the owner's real Gmail address is committed in `.env.example:47`, `app/momo.tsx:119,126` and `docs/EMAIL_SETUP.md`.
- **Environment sprawl.** `.env.example` documents ~31 names but omits the actual fail-closed gates (`TURNSTILE_ENABLED`/`SITE_KEY`/`SECRET_KEY`, `MOMO_SEAT_SIGNING_SECRET`, `MOMO_IMAGE_UPLOADS_ENABLED`, `MOMO_SECURITY_AXIOM_*`, `ADMIN_EMAILS`, `MOMO_PLATFORM`/`MOMO_TARGET`), and `vercel.json` declares none. Legacy Turso/LIBSQL variables are still listed.
- **Accessibility and locale.** `.icon-button` report flag is ~24 px at `#9a9087` on paper (~3.0:1) (`app/globals.css:32`); `.hint`/`.tiny-note` are 13 px muted; `.button.small` and tab padding fall under 44 px (`app/globals.css:37,48`). `lang="en"` (`app/layout.tsx:39`) wraps untranslated Hindi with no `lang` spans; `en-IN` and `Asia/Kolkata` are hardcoded throughout.
- **Maintainability.** `app/api/community/route.ts` is 149 lines / 28.7 KB and `app/momo.tsx` 129 lines / 28.9 KB, with individual lines reaching ~2 KB. `eslint.config.mjs` loads only next core-web-vitals plus TypeScript — no `max-len`, no formatter, no format script. Diffs are unreviewable, all authorization branches sit in one untestable dispatcher, and the tested/untested boundary is invisible.
- **Dead code.** `lib/connector*.ts/mts` (five files) have zero references from `app/` or `lib/`; `build/`, `vendor/` and `examples/d1/` are tracked but eslint-ignored and unreferenced; tests write bundles into a shared `work/tests/` so parallel runs collide, and four tests fail confusingly when `dist/` is stale.
- **Untested code paths with real risk.** `app/api/phone-verification/route.ts` is referenced by zero tests (OTP expiry, reuse, rate limit); the calendar route's auth and private-token leakage; `lib/email-provider.ts` Gmail path (only intercepted Resend is exercised); `lib/whatsapp.ts` real send; `lib/member-lifecycle.ts` pause/restore side effects; `scripts/embed-migrations.mjs` and `scripts/cloudflare-migrate.mjs`; `lib/device-session.ts` cookie flags and rotation.

## Recommended sequence

1. Rotate the D1/R2 credentials in `.env.cloudflare.local`, delete the file, and replace `ADMIN_EMAILS` with either a real implementation or a documentation correction.
2. Add one CI workflow running typecheck, lint and the disposable integration suites on push and PR; add a `test` script so it has something to call.
3. Fix the gateway format comparison and make `tests/image-sanitizer.integration.mjs` return a short format, so the suite can catch this class of bug again.
4. Make server errors 503 and log them; then bucket host-login failures by IP and rate-limit seat creation, uploads and reports.
5. Decide the one membership model (seat vs email place), then wire plan-publish notification and the Attend path for one-tap joiners.
6. Add `events.capacity` as a real column enforced at attendance-write time, plus the post-event minimum: reminder, no-show state, feedback.
7. Only then re-open the launch gates in the order the docs specify: Turnstile replay fix → Axiom alerts → Gmail authorization → one real Kitab Ghar plan → physical-device QA → pilot.
